# LV Transport Platform — Controlled First Real Ride Test Plan

Date: 2026-05-12  
Scope: First controlled **real** ride (single vehicle, supervised)  
Objective: Validate end-to-end operational flow in production-like conditions without changing architecture, features, or UI.

---

## 0) Preconditions and Control Setup

- Test window approved by operations lead (off-peak preferred).
- One designated test customer account, one dispatcher/admin account, one driver account.
- One designated test vehicle and driver physically available.
- GPS/location permissions enabled on driver device; mobile data available on both customer and driver devices.
- Payment method set to test-safe approach allowed by current deployment policy (e.g., low-cost ride route).
- Support/ops observer assigned to record timestamps and screenshots.
- Emergency stop contact list shared (ops lead, dispatcher, driver).

Expected result:
- Team, accounts, devices, and route are confirmed ready before live booking starts.

---

## 1) Step-by-step real ride test procedure + expected result

### Step 1 — Customer creates a test booking
Procedure:
1. Customer logs into the customer app.
2. Enter pickup and dropoff within pre-approved short route.
3. Confirm ride options and submit booking.
4. Capture booking ID and booking creation timestamp.

Expected result:
- Booking is created successfully with visible booking ID/status (e.g., Requested/Pending).
- Customer receives immediate booking confirmation in app.

### Step 2 — Admin receives and assigns the ride
Procedure:
1. Dispatcher/admin opens control tower booking queue.
2. Locate the newly created booking by ID/time/customer.
3. Assign booking to designated test driver.
4. Record assignment timestamp.

Expected result:
- Booking appears in admin queue quickly and transitions to assigned state.
- Assigned driver details are stored and visible in control tower.

### Step 3 — Driver accepts the ride
Procedure:
1. Driver logs into driver app and confirms availability.
2. Observe incoming assignment notification.
3. Accept the assigned ride.
4. Record acceptance timestamp.

Expected result:
- Driver receives the assigned job and can accept without error.
- Ride status updates to accepted/driver en route in admin + customer views.

### Step 4 — GPS/tracking is enabled
Procedure:
1. Driver app remains in foreground with location enabled.
2. Driver begins movement toward pickup point.
3. Observer checks live map/position updates from admin control tower.

Expected result:
- Driver location updates continuously (no long freezes).
- Admin map reflects current driver trajectory toward pickup.
- Customer sees driver approaching pickup.

### Step 5 — ETA/status updates are checked
Procedure:
1. During approach, compare ETA shown in customer app vs admin.
2. Move through normal status transitions: En Route → Arrived → In Progress.
3. Record timestamps of each state transition.

Expected result:
- Status transitions occur in correct order without manual data fixes.
- ETA updates are plausible and refresh during movement.
- No stuck status or conflicting state between apps.

### Step 6 — Ride is completed
Procedure:
1. Driver starts trip at pickup and drives approved route.
2. On arrival at destination, driver marks trip complete.
3. Record completion timestamp and final distance/time if displayed.

Expected result:
- Trip can be started and completed from driver app.
- Completion status propagates to admin + customer promptly.

### Step 7 — Pricing/payment/booking record is reviewed
Procedure:
1. Customer verifies fare shown after completion.
2. Admin verifies booking record includes key lifecycle timestamps.
3. Review payment state (success/pending/failure) as generated by existing system behavior.
4. Cross-check booking ID consistency across customer/admin/driver references.

Expected result:
- Final fare is produced and visible according to current pricing logic.
- Booking history and operational timeline are auditable in admin.
- Payment status is consistent with transaction outcome and no duplicate charge appears.

---

## 2) What to check on customer app

- Booking creation success + clear booking identifier.
- Ride state progression visibility: requested, assigned, driver en route, arrived, in progress, completed.
- Driver identity/vehicle details consistency once assigned.
- Live vehicle movement and ETA behavior during approach/trip.
- Final fare visibility and payment result messaging.
- Trip history entry created after completion.

Pass condition (customer app):
- Customer can book, track, complete, and view final ride outcome without inconsistent states.

---

## 3) What to check on admin control tower

- New booking ingestion latency (from creation to queue visibility).
- Manual assignment workflow functions for the designated driver.
- Ride state synchronization with driver/customer sides.
- Live telemetry updates (location path, freshness of updates).
- Lifecycle auditability: created/assigned/accepted/started/completed timestamps.
- Fare/payment state reflects post-ride result.
- No orphan ride state, duplicate assignment, or impossible status transitions.

Pass condition (admin):
- Dispatcher can manage full lifecycle from queue to completion with coherent state and logs.

---

## 4) What to check on driver app

- Assignment notification delivery and openability.
- Accept action reliability (single tap, no repeated error state).
- Navigation/location permission handling during trip.
- Start ride and complete ride controls behave correctly.
- Connectivity resilience: brief network jitter should not force app restart or lose ride context.

Pass condition (driver app):
- Driver can receive, accept, execute, and complete trip while location updates remain active.

---

## 5) Failure checklist (if any mismatch occurs)

Mark incident as fail candidate if one or more occur:

- Booking not visible in admin within operationally acceptable window.
- Assignment fails or appears on wrong driver.
- Driver cannot accept assigned ride.
- GPS not updating / stale location for extended interval.
- ETA not updating or obviously invalid while movement continues.
- Status order violation (e.g., completed before in-progress).
- Completion not propagated to all surfaces.
- Fare missing/incorrectly blank, payment status unknown, or duplicate charge.
- Booking IDs differ across systems for same ride.
- Critical UI blocking error requiring app restart to continue core flow.

For each failure capture:
- UTC timestamp, user/account, booking ID, device type/OS, screen, exact action, observed vs expected, screenshot/log snippet.

---

## 6) Rollback / safety procedure

If safety or major operational fault occurs:

1. **Stop test expansion immediately** (no additional real bookings).
2. Dispatcher sets affected booking to safe operational handling path (per current admin capabilities).
3. Driver follows dispatcher instruction; prioritize passenger safety and legal road behavior.
4. If payment anomaly appears, flag booking for manual reconciliation before further tests.
5. Move system to “test hold” mode operationally (process-level hold; no architecture change).
6. Create incident record with booking ID, severity, and impacted module.
7. Resume testing only after go/no-go review by ops + engineering owner.

Safety rule:
- Human safety and legal compliance override test completion at all times.

---

## 7) Final pass/fail criteria

A **PASS** requires all of the following in one controlled ride:

- End-to-end lifecycle completes successfully (create → assign → accept → track → complete → reconcile).
- State is consistent across customer, admin, and driver interfaces.
- GPS/ETA/status updates are operationally credible throughout ride.
- Final fare/payment/record is present and internally consistent.
- No critical blocker or safety escalation triggered.

A **FAIL** is declared if:

- Any core lifecycle step cannot be completed without workaround,
- Cross-surface state divergence persists,
- Tracking or completion is operationally unreliable,
- Payment/fare outcome is non-reconcilable,
- Safety rollback procedure is invoked.
