# Operational Design System

## Purpose

Define the unified operational visual language for LVTransport.

This system governs:

- customer experience
- driver cockpit
- admin tower
- Founder OS
- realtime telemetry
- operational intelligence
- incident visibility

## Design philosophy

LVTransport is not a generic mobility UI.

It is:

- operational
- realtime
- intelligence-driven
- telemetry-aware
- recovery-aware

The interface must communicate operational confidence.

## Primary UX modes

### Customer UX

Goals:

- premium
- calm
- trustworthy
- minimal friction

Visual traits:

- cinematic dark mode
- gold operational accents
- low-noise UI
- simplified actions
- trust indicators

### Driver Cockpit

Goals:

- clarity
- speed
- focus
- low cognitive load

Visual traits:

- large touch targets
- realtime navigation emphasis
- operational status visibility
- minimal distractions
- high contrast telemetry

### Admin Tower

Goals:

- density
- fleet visibility
- operational awareness
- incident response

Visual traits:

- multi-panel dashboards
- live maps
- telemetry overlays
- incident highlighting
- operational timelines

### Founder OS

Goals:

- executive intelligence
- operational confidence
- strategic visibility
- anomaly detection

Visual traits:

- intelligence cards
- confidence scoring
- replay access
- runtime health prominence
- financial pulse visibility

## Color system

### Runtime states

Healthy:
- green

Degraded:
- amber

Recovering:
- blue

Critical:
- red

Unknown:
- gray

### Operational accents

Primary accent:
- operational gold

Telemetry:
- cyan

Incidents:
- orange/red

Replay:
- violet

AI systems:
- purple

## Typography system

Customer:
- elegant
- premium
- spacious

Driver:
- large
- high readability
- fast scanning

Admin:
- dense
- data-first

Founder:
- intelligence-first
- hierarchy-focused

## Realtime indicators

Every realtime panel must show:

- connection state
- last update timestamp
- degraded fallback state

Indicators:

- live
- delayed
- polling fallback
- disconnected

## Telemetry philosophy

Telemetry must feel:

- alive
- operational
- explainable

Never decorative.

Every chart must answer:

- what changed
- why it changed
- whether action is needed

## Map philosophy

Maps are operational tools.

Maps must show:

- drivers
- active trips
- incidents
- zones
- runtime degradation
- replay movement

## Incident UX rules

Critical incidents:

- interrupt UI
- impossible to ignore

Degraded systems:

- visible but non-blocking

Recovered systems:

- visibly marked as stabilized

## Motion system

Motion exists only to communicate:

- state change
- runtime transition
- telemetry updates
- incident escalation
- recovery completion

Never decorative animation.

## Governance rules

- All operational states map to runtime contracts.
- All realtime systems require polling fallback.
- Founder OS always exposes runtime health.
- Incident visibility cannot be disabled.
- Operational timestamps are mandatory.
- Replay views must support auditability.
